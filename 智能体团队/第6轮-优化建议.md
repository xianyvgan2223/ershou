## 二、逐项说明

### P0-1 内部接口鉴权（`/inner/**`）
- **现状**：item-service 的 `/inner/items/{id}`、`/inner/items/{id}/lock` 仅靠"不经过网关"来保护；服务端口 8082 若被直接访问（同机/内网），可绕过网关鉴权扣库存。
- **建议**：① 网关路由层显式拒绝 `/inner/**`；② 内部调用加共享密钥（`X-Internal-Token`，Feign 拦截器统一注入）或 mTLS；③ 生产用网络策略/安全组只允许服务间访问。
- **涉及**：`ershou-cloud-gateway/.../GatewayRoutesConfig.java`、`ershou-item-service/.../controller/InnerItemController.java`、`ershou-order-service/.../feign/ItemClient.java`。

### P0-2 MQ 可靠消息
- **现状**：`OrderEventPublisher` 在 `AFTER_COMMIT` 里发送，失败只打日志（订单已提交但消息丢失 → `sale_count` 少加、缓存未清）；DLQ（`ershou.item.order-created.dlq`）存在但没有消费者/告警。
- **建议**：① 本地消息表（outbox）：订单事务内写一条"待发送"记录，事务提交后异步投递并标记，定时任务补偿重发；② 或引入 RocketMQ 事务消息；③ 为 DLQ 增加消费端（记录+告警+人工重放），并加 Prometheus 指标。
- **涉及**：`ershou-order-service/.../service/OrderEventPublisher.java`、`service/MeetupOrderService.java`、`ershou-item-service/.../mq/OrderCreatedListener.java`。

### P0-3 中间件安全与持久化
- **现状**：Nacos `NACOS_AUTH_ENABLE=false`（演示方便）；Nacos 管理员/数据库密码明文；Seata Server 使用默认 secretKey、store=file 单机；Sentinel Dashboard 无鉴权、规则在代码里（Dashboard 改规则不会持久化）；Redis 6380 有密码但网关 CORS 全放行、Actuator 端点未统一收敛。
- **建议**：Nacos 开启鉴权并改强密码（或内网+IP 白名单）、配置加密（Nacos 加密插件/环境变量注入）；Seata 换 2.x 客户端/服务端对齐或固定版本并设置自定义密钥、store 改 DB；Sentinel 规则持久化到 Nacos datasource；Actuator 仅暴露 health/info 并加鉴权。

### P0-4 管理端权限逐接口核查
- **现状**：需以本轮 T36 审计结果为准（`AdminAuthService.requireAdminId()` 覆盖情况、平台运营台 18 个接口）。
- **建议**：统一在网关或 AOP 做管理员校验（`@RequireAdmin` 注解），避免"某个接口漏写"；对管理接口加操作审计日志（谁、何时、改了什么）。

### P0-5 敏感配置与密钥
- **现状**：数据库/Redis 密码出现在 Nacos 配置、`.env`、脚本、docker compose 中；SSH/云 key 未见（无关）。
- **建议**：生产用环境变量/密钥管理（Vault/K8s Secret）；仓库内 `.env` 已 gitignore 但需检查历史提交；日志中脱敏手机号/token。

### P1-1 全链路追踪与日志
- **现状**：common 里只有 TraceId 过滤器（透传），没有采集；各服务日志分散。
- **建议**：Spring Boot 3 + Micrometer Tracing（Brave/OTel）+ Zipkin/Jaeger（Docker 加一个容器即可），Gateway/Feign/RabbitMQ 自动传播 traceId；JSON 结构化日志 + Loki/ELK；答辩可展示一条"下单"完整链路。
- **涉及**：所有服务 pom + Nacos 配置 + docker-compose。

### P1-2 网关动态路由与灰度
- **现状**：路由硬编码在 `GatewayRoutesConfig`（改路由要改代码重启）；无灰度/权重。
- **建议**：Nacos 配置文件或数据库驱动动态路由；按 header/用户比例灰度；路由级超时/重试/熔断策略外置。

### P1-3 剩余模块迁移与 API 契约
- **现状**：chat/admin/map/platform/search/cart/favorites 仍由网关反代旧单体（8080），属于绞杀者过渡。
- **建议**：按 `docs/migration-roadmap.md` 的 5 阶段继续；先用 springdoc-openapi 生成各服务契约，网关聚合 Swagger UI，作为服务间契约与验收依据。

### P1-4 数据一致性（旧库↔新库）
- **现状**：`migrate-data.ps1` 是一次性快照迁移，之后新服务写入不回写旧库；旧单体仍在写旧库（若继续使用会双源不一致）。
- **建议**：① 明确"旧库停写"时间点；② 双写过渡或 CDC（Canal/Debezium）同步；③ 对账任务（定时比对关键表行数/金额/库存）+ 差异修复；④ 数据迁移纳入发布流程。

### P1-5 分布式 ID 与幂等
- **现状**：订单号 `genOrderNo()` 为时间戳+随机（需确认，若仅时间戳有并发重复风险）；下单无客户端幂等键。
- **建议**：雪花算法（Leaf/Snowflake）生成订单号；下单接口要求 `Idempotency-Key`（Redis SETNX），重复请求返回同一订单；MQ 消费幂等已做，可复用同一套工具。

### P1-6 高可用
- **现状**：Nacos standalone（volumes 持久化但单节点）、RabbitMQ 单节点、Redis 单节点、Seata file store、MySQL 单机。
- **建议**：生产按需升级：Nacos 3 节点+MySQL、RabbitMQ 集群+镜像队列、Redis 哨兵/集群、Seata DB 存储+集群、MySQL 主从；课程演示可用 docker compose profile 做"多实例"演示。

### P1-7 缓存与性能
- **现状**：item 详情缓存 60s，无空值缓存/互斥重建；列表查询未接 ES（云 item-service 用 MySQL LIKE 降级）；Feign 超时/重试未细化；分页 `pageMax` 已有上限。
- **建议**：空值缓存/布隆过滤器防穿透、逻辑过期/互斥锁防击穿、随机 TTL 防雪崩；搜索接 ES；Feign connect/read timeout、重试退避、隔离仓；连接池/线程池指标与容量评估；慢 SQL 监控。

### P2-1 测试与 CI/CD
- **现状**：基本无单元测试；验收靠脚本（`scripts/verify-*.ps1`、`cloud-demo.ps1`）。
- **建议**：核心逻辑（下单/库存/秒杀/优惠券）加 JUnit + Testcontainers 集成测试；CI（GitHub Actions）做编译+测试+镜像构建；把现有验收脚本接入 CI 作为冒烟。

### P2-2 监控告警
- **建议**：各服务 Actuator + Micrometer → Prometheus → Grafana（JVM、HTTP、连接池、RabbitMQ、Sentinel 指标）；告警规则（错误率、P99、队列堆积、Seata 回滚数）。

### P2-3 代码质量
- **建议**：`common` 拆分（core/web/data，避免每个服务被强制带 mybatis/sa-token 依赖）；Checkstyle/SpotBugs/SonarQube；API 文档；统一错误码文档；模块边界评审。

### P2-4 安全加固（与漏洞审计联动）
- **建议**：HTTPS（生产）+ mTLS（服务间）；CORS 白名单（当前全放行）；CSRF 防护（纯 token 无 cookie 风险较低，但管理端需确认）；token 短期 + refresh token（当前 10 年）；真实短信验证码（当前 mock 123456 仅演示）；登录/发码限流与图形验证码；上传文件类型/大小/病毒扫描；防重放（时间戳+nonce+签名）；安全响应头（CSP/X-Frame-Options 等）。

### P2-5 业务完善
- 订单超时未面交自动关闭（延迟队列/RabbitMQ TTL+DLX 或 RocketMQ 延迟消息）
- 库存回补与对账（取消/超时/退款）
- 站内信/推送（平台审核结果、订单状态变更）
- 评价体系、信用分闭环、举报与风控
- 平台代卖：退款/售后、结算、发票（演示可暂不做）
- 搜索：ES 接入 + 搜索建议/热度排序
- 推荐：基于浏览/收藏的简单召回（课程演示可选）

### P2-6 演示交付（答辩加分）
- **一键脚本**：`start-all.ps1`（docker compose up → 发布 Nacos 配置 → 4 个服务 + 旧单体 → 健康检查 → 打印就绪表格）、`stop-all.ps1`、`reset-demo-data.ps1`。
- **故障演练脚本**：演示 Sentinel 限流（并发打 items 看 429）、Feign 降级（停 item-service 下单返回 90001）、Seata 回滚（debugFail）、MQ 解耦（看 sale_count 变化）、Nacos 热更新（改 max-qty 立即生效）。
- **展示材料**：架构图（已有 mermaid）、一次下单的链路追踪截图、压测对比数据（单体 vs 微服务）、演示录屏。
- **数据准备**：固定演示账号/商品/券，重置脚本保证每次演示一致。

## 三、建议实施顺序（按"性价比"）

1. **答辩前（0.5–1 天）**：P2-6 一键脚本 + 故障演练脚本 + 演示数据重置；把现有 11 步 E2E 和 4 个演练做成"一条命令可复现"。
2. **紧接着（1–2 天）**：P0-1 内部鉴权、P0-2 MQ outbox/DLQ 消费、P0-3 中间件安全（Nacos 鉴权/Seata 密钥/Sentinel 规则持久化）。
3. **中期（3–5 天）**：P1-1 全链路追踪、P1-2 动态路由、P1-3 API 契约、P1-7 缓存治理。
4. **长期（1–2 周）**：P1-4 数据一致性、P1-5 分布式 ID/幂等、P1-6 高可用、P2 测试/CI/监控/安全加固/业务完善。
