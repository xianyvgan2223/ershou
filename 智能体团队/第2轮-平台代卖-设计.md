## 一、目标与范围

### 要交付的 4 件事（用户需求）
1. **平台作为卖家的交易功能**：商品 seller 是平台官方账号（不是个人），买家可直接下单，走现有面交/自提单状态机。
2. **首页对平台商品特殊标注**：商品卡片出现「官方代卖」标识，可点进平台专区。
3. **管理员管理平台代卖地点**：后台可增删改查代卖/自提点（名称、校区、地址、经纬度、营业时间、联系电话、指引、启停、排序）。
4. **新增平台商品页面**（`/platform`），**预留优惠券 + 商品秒杀**，用 Redis 做出真实亮点：
   - 缓存：代卖点列表 / 券列表 / 秒杀场次（`JsonCache` + TTL）
   - 原子扣减：优惠券库存、秒杀库存用 **Lua 脚本**（防超卖）
   - 限购：Redis Hash（`perUserLimit`）
   - 限流：`INCR + EXPIRE`（抢券/抢购 5 秒 1 次）
   - 预热与重建：启动 `ApplicationRunner` 预热 + 后台刷新接口 + **SETNX 分布式锁**防多实例重复预热
   - 幂等：DB 唯一键兜底（`platform_coupon_user`、`platform_seckill_record`）

### 本轮不做（明确留白，写进文档）
- 移动端（Flutter）平台专区与角标（下轮）
- 地图上叠加代卖点图层（下轮）
- 优惠券在下单时的**实际抵扣结算**（本轮只做领取+我的券+预留字段；下单接口保留 `couponId` 入参但暂不抵扣，代码注释标 `TODO(round3)`)
- 秒杀支付与超时释放的完整订单履约（本轮抢购成功即生成平台单，履约走现有面交单）

## 二、平台卖家账号与数据模型

### 2.1 平台官方账号（固定 id=1000）
`sys_user.id = 1000`，`nickname='校园二手官方严选'`，`role_flags=16`（**新增位标记：16=平台自营**，与既有 1=普通/2=多库存商家/4=代卖员/8=运营 不冲突），`identity_flag=1`（商家徽章），`status=1`。
该账号**不可登录**（不写入可登录手机号；`phone_hash = SHA2('ershou-platform-seller',256)`）。
配置项（`PlatformProperties`，用 `@Value` 默认值，不改 `application.yml`）：
- `ershou.platform.seller-id: 1000`
- `ershou.platform.seller-nickname: 校园二手官方严选`
- `ershou.platform.item-valid-days: 30`（平台商品有效期）
- `ershou.platform.lock-hours: 168`（平台单自提窗口 7 天）

### 2.2 表结构（`sql/migration-platform.sql`，幂等可重复执行）
| 表 | 作用 | 关键字段 |
| --- | --- | --- |
| `item`（ALTER） | 标记平台商品 | `seller_type TINYINT NOT NULL DEFAULT 1`（1=个人 2=平台）、`platform_point_id BIGINT NULL`、`KEY idx_item_platform(seller_type,status,campus_id)` |
| `platform_consign_point` | 代卖/自提点（管理员维护） | campus_id, name, address, lng, lat, open_hours, contact_phone, guide_text, cover_url, sort, status(1启用/0停用) |
| `platform_coupon` | 优惠券模板 | campus_id, name, type(1满减/2折扣), threshold_amount, discount_amount, discount_rate, total_stock, per_user_limit, start_at, end_at, status |
| `platform_coupon_user` | 用户已领券 | coupon_id, user_id, status(1未用/2已用/3过期), received_at, used_at, order_id, **UNIQUE(coupon_id,user_id)** |
| `platform_flash_sale` | 秒杀场次 | campus_id, title, start_at, end_at, status(1预告/2进行中/3结束), sort |
| `platform_flash_sale_item` | 场次商品 | flash_sale_id, item_id, seckill_price, seckill_stock, sold_count, per_user_limit, sort, **UNIQUE(flash_sale_id,item_id)** |
| `platform_seckill_record` | 抢购成功记录（DB 真值，用于预热重建/已抢判断） | item_id, user_id, order_id, price, created_at, **UNIQUE(item_id,user_id)** |

**种子数据（迁移脚本内，全部幂等）**：
- 平台账号 id=1000（`ON DUPLICATE KEY UPDATE`）
- 代卖点 3 个（campus_id=2，坐标从 `trade_point` 现有行 `INSERT ... SELECT` 复制，保证真实可用）
- 平台商品 4 件（`INSERT ... SELECT` 从现有在售个人商品复制图片/分类，`title=CONCAT('[官方严选] ', ...)`，价格 85 折，`seller_type=2`，`status=2`，`expire_at=+30天`；`WHERE NOT EXISTS` 保证只插一次）
- 优惠券 3 张（满50减8 / 满100减20 / 满30打9折）
- 秒杀场次 1 个（`start_at=NOW()-10min, end_at=NOW()+3DAY, status=2`）+ 2 个秒杀商品（平台商品 6 折，`seckill_stock=5`）

### 2.3 状态与状态机
- **平台商品不进入"锁定"态**（v1.1 修正）：`item.status=2`（在售）→ 每次成交只做**条件扣库存**（`stock=stock-数量`）；库存归零时置 `status=4`（已售出）。**不要写 status=3 / lock_user_id / lock_expire_at** —— 否则多库存秒杀会退化成串行（5 份库存只有 1 单能成功），且现有解锁任务会把平台位置为失效。
  - 独品（`is_unique=1` / stock=1）：首次成交库存归零即 status=4。
  - 多库存：status 保持 2，直到 stock=0；并发由条件更新 `WHERE stock>=数量` 保证不超卖。
- 平台单：复用 `meetup_order`，`status=2`（待自提），`seller_id=1000`，`seller_confirm_at=NOW()`（平台自动确认接受），`point_id=platform_point_id`，`deal_price=成交价`（秒杀价或商品价），`remark='平台代卖自提单'`，**不设 time_slot / 不依赖 lock_expire_at**。
- 买家点「我已收到」→ 平台单直接完成：`status=3`（已完成），不做 `markSold`（会清多库存），只把平台商品按"stock>0→status=2 / stock=0→status=4"收口；买家 +2 信用分，平台账号不加分、不写 credit_log。
- 平台单取消/拒绝 → **还库存**（`stock=stock+quantity`），商品若已 status=4 且库存恢复则回 status=2。
- **并发预期（秒杀验收口径）**：库存 5 份时，5 个不同用户并发抢购应全部成功、第 6 个失败；同一用户受 `per_user_limit` 限制。QA 按此断言。

### 3.5 跨模块契约：`OrderService.platformBuy`（由 order-member 实现，platform-dev 调用）
```java
/** 平台代卖下单：平台商品直购/秒杀成功后建单。返回值至少含 orderId, orderNo, itemId, dealPrice, pointId, itemTitle, itemCover。 */
public Map<String, Object> platformBuy(Long itemId, Long buyerId, Integer quantity, java.math.BigDecimal dealPrice, Long pointId);
```
实现要求（order-member，**v1.1 修正版**）：
1. 前置校验：item 存在、`seller_type=2`、`status=2`、`stock >= quantity`；`quantity` 夹取 ≥1。
2. **条件扣库存（不锁库、不写 status=3）**：`UPDATE item SET status=IF(stock-?<=0,4,2), stock=stock-?, version=version+1 WHERE id=? AND seller_type=2 AND status=2 AND stock>=?`，0 行 → 抛 `BizException(ITEM_LOCKED)`（或等价错误码）。**不要写 lock_user_id / lock_expire_at**，否则多库存秒杀退化为串行、且会被定时任务误伤。
   - ⚠️ **MySQL 单表 UPDATE 的赋值按从左到右求值**：必须**先算 `status` 再扣 `stock`**（写反会读到扣减后的库存，stock=5 买 3 件会误判售罄）。这是 order-member 在返工时发现并修正的，勿改回。
3. 插入 `meetup_order`：status=2、seller_id=平台账号、seller_confirm_at=NOW()、point_id=平台点、deal_price=成交价、quantity、remark='平台代卖自提单'、order_no 用现有生成器；**不写 time_slot_*、不设锁**。
4. 事务后：同步 ES 索引 + 清 item 缓存（平台单不发私聊给平台账号；通知买家可选）。
5. **信用分**：平台账号不参与 +2（完成时判定 seller_id=1000 跳过）；买家仍正常 +2。
6. 买家「我已收到」完成平台单：`status=3` + 商品按 stock 收口（>0→2，=0→4），不用 `markSold`（会清多库存）；finished 影响 0 行 → 抛错回滚。
7. 取消/拒绝平台单：还库存 + 商品状态回 2（若因库存归零被置 4）。
8. **并发验收**：库存 5 份，5 个不同用户并发直购/抢购应全部成功（各生成一张平台单），第 6 个失败；同一用户超 `per_user_limit` 失败。

## 四、Redis 设计（`platform/config/PlatformCacheKeys.java`）

| Key | 类型 | 说明 |
| --- | --- | --- |
| `ershou:platform:points:{campusId}` | String(JSON) | 代卖点列表缓存，TTL 10min，后台增删改即删 |
| `ershou:platform:coupons:{campusId}` | String(JSON) | 可领券列表缓存，TTL 60s |
| `ershou:platform:overview:{campusId}` | String(JSON) | 专区概览聚合缓存，TTL 60s |
| `ershou:platform:flash:{campusId}` | String(JSON) | 当前秒杀场次缓存，TTL 30s |
| `ershou:platform:coupon:stock:{couponId}` | String(int) | 券剩余库存（Lua 扣减），TTL 到 end_at+1h |
| `ershou:platform:coupon:users:{couponId}` | Hash(userId→已领张数) | 限领判定 |
| `ershou:platform:seckill:stock:{itemId}` | String(int) | 秒杀剩余库存（TTL 到 end_at+1h） |
| `ershou:platform:seckill:users:{itemId}` | Hash(userId→已买数) | 限购判定 |
| `ershou:platform:rate:claim:{userId}` / `ershou:platform:rate:grab:{userId}` | String | 限流：INCR + EXPIRE 5s，>1 拒绝（code=-4） |
| `ershou:platform:lock:warmup` | String | `SET NX EX 30` 预热分布式锁 |

> **TTL 实现说明**：表中所列为**设计上限**；代码实际取上限的 90%（如 points 9min、coupons 54s、overview 54s、flash 27s），给 `JsonCache` 的序列化/时钟抖动留余量。验收断言按「0 < TTL ≤ 上限」，不要断言等于设计值。

**Lua 脚本（`src/main/resources/lua/`）**
`coupon_claim.lua` / `seckill_grab.lua`（参数：KEYS[1]=stock, KEYS[2]=users hash；ARGV[1]=userId, ARGV[2]=limit）：
```
stock==nil → -1（未预热）
stock<=0  → 0（已抢完）
HGET(users,userId) >= limit → -2（超限）
DECR stock; HINCRBY users userId 1; → 1（成功）
```
**预热 `PlatformCacheWarmup`（ApplicationRunner，幂等）**：
- 拿 `ershou:platform:lock:warmup` 锁，拿不到就跳过
- 券：`leftStock = total_stock - COUNT(platform_coupon_user)`，若 Redis key 不存在则写入 + 按 DB 回填 users hash；TTL 到 end_at+1h
- 秒杀：`leftStock = seckill_stock - COUNT(platform_seckill_record)`；同样回填 users hash
- 后台 `POST /api/v1/platform/admin/cache/refresh` 强制重建（先删 key 再预热）

## 七、验收标准（QA 必须逐条给证据）

1. 后端编译：`mvn -DskipTests compile` 成功（0 错误）。
2. Web 构建：`npm run build`（`vue-tsc --noEmit && vite build`）成功。
3. 迁移落库：`sql/migration-platform.sql` 在现有库执行成功且**可重复执行**（第二遍不报错、不重复插入）；`item.seller_type` 列存在、`platform_*` 6 张表存在、种子 4 商品/3 券/1 场次/3 点位。
4. 运行时（后端 8080 起 + Redis）：
   - `GET /api/v1/platform/shop/points?campusId=2` 200 且 ≥3 条
   - `GET /api/v1/platform/shop/items?campusId=2` 200 且 ≥4 条、`sellerType=2`
   - `GET /api/v1/platform/shop/coupons?campusId=2` 200 且含 leftStock
   - `GET /api/v1/items?pageNum=1` 中平台商品返回 `sellerType=2`（首页标注数据源）
   - 领券：POST claim 成功 → DB `platform_coupon_user` +1、Redis stock -1；重复领取返回超限；并发 10 次请求库存不为负
   - 抢购：POST grab 成功 → 生成 `meetup_order`（status=2、seller_id=1000、point_id=代卖点）+ `platform_seckill_record`；Redis stock -1；再抢返回超限/已抢完
   - 管理员接口：无 admin 权限 → 403/无权限；admin 登录后 CRUD 代卖点成功，新增点位出现在 shop/points
   - 平台直购：`POST /me/items/{id}/buy` 成功建单、商品状态变 3、买家 `/meetup-orders` 能看到
5. Redis 证据：`docker exec ershou-redis redis-cli -a <pwd> --scan --pattern 'ershou:platform:*'` 列出全部 key，并贴出 stock/users hash 的值。
6. Web 页面：`vue-tsc` 通过 + 截图证据（如可用 puppeteer-core）：`/platform` 页面、首页平台角标、`/admin/platform-points`。
7. 回归：登录、首页列表、商品详情、购物车、面交单页面不报错（至少接口级 200）。
8. 无源码泄漏改动：`git status` 只含预期文件。
