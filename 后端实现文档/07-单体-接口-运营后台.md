# 07 · 单体接口：运营后台（admin）

> 代码位置：`ershou-server`（Spring Boot 3.3.5 + MyBatis-Plus 3.5.9 + Sa-Token 1.39.0 + JDK 21，单体）。
> 覆盖 `module/admin` 的 3 个 Controller，共 **25 个接口**：审核工作台 10 个、管理与审计 8 个、上架审核 7 个。
> 另含 1 条 WebSocket 推送通道（`/ws/admin/review`，不占 HTTP 接口数）。文档基于 2026-10-30 的源码快照；未在源码中出现的行为不写，不确定处标注「以源码为准」。

## 一、模块概览

| 项 | 内容 |
| --- | --- |
| 基础路径 | `/api/v1/admin`（`AdminAuditController`、`AdminManageController` 类级路径相同）；`/api/v1/admin/review`（`AdminReviewController`） |
| 统一返回 | `Result<T> = {code, message, data, traceId}`；成功 `code=0`、`message="ok"`；业务错误 HTTP 仍为 200，靠 `code` 判断 |
| 分页返回 | `PageResult<T> = {total, pageNum, pageSize, records}`（字段名是 `records`，不是 `list`） |
| 鉴权 | 全部接口需登录 + **运营权限**；见下文「运营权限判定」 |
| 登录态载体 | 请求头 `Authorization: Bearer <token>`（Sa-Token，`token-name=Authorization`、`token-prefix=Bearer`） |
| 涉及表 | `item_review`（上架审核队列）、`sys_audit_log`（运营操作审计）、`credit_log`（信用分流水）；联查 `item`、`trade_point`、`sys_user`、`meetup_order`、`item_category`、`campus` |
| 关联缓存 | Redis：`ershou:admin:dashboard`（概览 30 秒读缓存）、`ershou:admin:review:channel`（跨实例广播频道）、`ershou:admin:review:online`（在线审核员 Hash） |
| 关键配置 | `ershou.admin.role-flag`（默认 8）、`ershou.admin.user-ids`（白名单）、`ershou.review.*`（见下）、`ershou.cache.dashboard-ttl`（默认 30s） |
| 审计口径 | 所有后台写操作都调用 `AuditLogService.record(...)` 落一条 `sys_audit_log`；写审计失败只告警，不影响主流程；每次写操作后（事务提交后）删除概览缓存 |

### 1.1 运营权限判定（必须照着实现）

全站唯一入口是 `AdminAuthService.requireAdminId()`：

1. `StpUtil.checkLogin()`：未登录抛 `NotLoginException` → 全局异常处理转 `code=10002`；
2. 取当前登录用户 id；
3. `isAdmin(userId)` 判定，满足任一即通过：
   - `userId` 命中 `AdminProperties.userIds` 白名单（`ershou.admin.user-ids`，环境变量 `ERSHOU_ADMIN_USER_IDS=1,2` 注入）；
   - 或 `sys_user.role_flags` 与 `roleFlag` **按位与不为 0**：`(roleFlags & 8) != 0`（`ershou.admin.role-flag` 默认 8，`schema.sql` 注释：1=普通 2=多库存商家 4=代卖员 8=运营）；
4. 通过后返回运营用户 id；不通过抛 `BizException(NO_PERMISSION, "需要运营人员权限")` → `code=10003`、`message` 为这句自定义文案。

补充：

- Sa-Token 拦截器只要求 `/api/**` 登录，`/api/v1/admin/**` **不在白名单**，所以未登录调用会先被拦截成 `10002`；Controller 内还会再校验一次运营身份。
- WebSocket `/ws/admin/review` **不经过 Sa-Token 拦截器**（`/ws/**` 不在拦截范围），由 `AdminReviewHandshakeInterceptor` 自行完成「token 有效 + 运营身份」两道校验：无 token / token 无效 → HTTP 401；token 有效但不是运营 → HTTP 403。
- 注意接口本身**没有**用 Sa-Token 注解角色（`@SaCheckRole`），运营身份完全由 `AdminAuthService` 判定。

### 1.2 响应格式与空字段

- Jackson 全局 `default-property-inclusion: non_null`，**值为 null 的字段不会出现在响应 JSON 中**（示例里保留 null 只为说明语义）。
- 日期格式 `yyyy-MM-dd HH:mm:ss`，时区 `Asia/Shanghai`。
- 分页参数统一 `pageNum`（默认 1）、`pageSize`（默认 20）；所有后台分页的 `pageSize` **上限 100**，超过按 100 截断，小于 1 按 1。
- 批量接口**不会因单条失败整批回滚**：返回 `success / failed / failures[{id, reason}]`。

### 1.3 统一错误码（本模块会真实出现的）

| code | 枚举 | 含义 | 典型触发 |
| --- | --- | --- | --- |
| 0 | `SUCCESS` | ok | 成功 |
| 10001 | `PARAM_ERROR` | 参数校验失败（message 为具体提示） | Bean Validation 失败、`action` 非法、批量上限、ids 为空、用户/点位不存在、信用分步长越界等 |
| 10002 | `NOT_LOGIN` | 未登录或登录已过期 | 无 token / token 失效 |
| 10003 | `NO_PERMISSION` | 无权限访问（message=`需要运营人员权限`） | 已登录但不是运营 |
| 30001 | `ITEM_NOT_FOUND` | 商品不存在或已删除 | 商品 id 查不到；上架审核记录不存在时也复用它并改文案 |
| 60001 | `ADMIN_ITEM_STATUS` | 当前商品状态不允许该审核操作 | 单条通过/驳回、强制下架的状态前置条件不满足 |
| 60002 | `ADMIN_POINT_STATUS` | 当前点位状态不允许该审核操作 | 点位非待审仍审核；重复启用/停用 |
| 60003 | `ADMIN_REASON_REQUIRED` | 请填写驳回原因 | 商品/点位驳回时模板 code 与补充说明都为空 |
| 60004 | `ADMIN_SELF_OPERATION` | 不能对自己执行该操作 | 修改自己的账号状态 |
| 61001 | `REVIEW_ALREADY_HANDLED` | 该商品已被处置，请刷新列表 | 上架审核「已审核」条件更新 0 行；上架审核「下架」商品已不可下架 |
| 61002 | `REVIEW_NOT_ACTIONABLE` | 该商品已不在可处置状态 | **源码中已定义但当前没有任何抛出处**（以源码为准） |
| 90001 | `SYSTEM_ERROR` | 系统开小差 | 未捕获异常兜底 |

## 二、数据模型简表

### 2.1 `item_review`（上架审核队列，实体 `ItemReview`）

一个商品只保留 **一条当前记录**（唯一键 `uk_item(item_id)`）；重新入队时在这条记录上累加 `revision`。历史处置记录走 `sys_audit_log`。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 自增 |
| `item_id` | BIGINT | 商品 id，唯一 |
| `seller_id` | BIGINT | 卖家 id（冗余，便于按人筛选） |
| `title` | TEXT | **入队时的标题快照**；改名场景存「改之前」的旧标题，供审核员对比 |
| `review_type` | TINYINT | 1=新上架 2=改名/改描述 3=到期重新上架 4=违规后二次申请 5=存量导入 |
| `revision` | INT | 内容修订号；首次 1，之后每次重新入队 +1 |
| `status` | TINYINT | 0=待审核 1=已审核（归档，默认列表不再显示） |
| `review_action` | TINYINT | 1=已审核（看过没问题） 2=已下架 |
| `queued_at` | DATETIME | 本轮入队时间（列表按其倒序） |
| `first_queued_at` | DATETIME | 该商品第一次进入审核页的时间 |
| `content_changed_at` | DATETIME | 最近一次改名/改描述时间（仅 TYPE_RENAMED 写） |
| `reviewer_id` | BIGINT | 处置人；**待审状态下恒为空**（无认领/抢单机制） |
| `claimed_at` | DATETIME | 认领时间（当前无认领导入，恒为空） |
| `reviewed_at` | DATETIME | 处置时间 |
| `note` | VARCHAR(255) | 审核备注 / 下架原因（接口侧截断 200 字符） |
| `created_at` / `updated_at` | DATETIME | 时间戳 |

枚举常量（`ItemReview`）：`STATUS_PENDING=0`、`STATUS_DONE=1`；`TYPE_NEW=1`、`TYPE_RENAMED=2`、`TYPE_RELIST=3`、`TYPE_VIOLATION_RELIST=4`、`TYPE_LEGACY=5`；`ACTION_REVIEWED=1`、`ACTION_OFFLINE=2`。

### 2.2 `sys_audit_log`（运营操作审计，实体 `SysAuditLog`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 自增 |
| `operator_id` | BIGINT | 操作人（运营用户 id） |
| `module` | VARCHAR(32) | 模块：`item` / `point` / `user` |
| `action` | VARCHAR(32) | 动作：`approve`、`reject`、`batch-approve`、`batch-reject`、`force-offline`、`review-item-reviewed`、`review-item-offline`、`update-status`、`adjust-credit`、`point-offline`、`point-online` 等 |
| `target_type` | VARCHAR(32) | 目标类型：`item` / `trade_point` / `user` |
| `target_id` | BIGINT | 目标 id；批量商品审核时为 null |
| `before_value` / `after_value` | JSON | 变更前/后快照（查询接口会还原成对象返回） |
| `ip` | VARCHAR(45) | 取 `X-Forwarded-For` 第一个值，否则 `getRemoteAddr()` |
| `created_at` | DATETIME | 时间戳 |

### 2.3 `credit_log`（信用分流水，实体 `CreditLog`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT PK | 自增 |
| `user_id` | BIGINT | 被调整用户 |
| `change_value` | INT | 实际变化值（正负；因下限 0 截断时可能小于请求值） |
| `before_score` / `after_score` | INT | 调整前 / 后分数 |
| `reason` | VARCHAR(64) | 原因；接口未传时写 `运营人工调整` |
| `biz_type` | VARCHAR(32) | 后台人工调整为 `admin` |
| `biz_id` | BIGINT | 业务单号（人工调整不写） |
| `operator_id` | BIGINT | 操作运营 id |
| `created_at` | DATETIME | 时间戳 |

### 2.4 `item` 状态码（本模块判断前置条件时使用）

| status | 文案（`ItemService.statusText`） | 说明 |
| --- | --- | --- |
| 0 | 草稿 | 不入审核队列 |
| 1 | 审核中 | 审核工作台的待审队列；**不在上架审核页** |
| 2 | 在售 | 上架审核页只关心 2/3 |
| 3 | 已锁定 | 买家约面交锁库中，仍属「挂在平台上」 |
| 4 | 已售出 | 不可再处置 |
| 5 | 已下架 | 上架审核「下架」的落点（非违规） |
| 6 | 审核未通过 | 审核驳回的落点 |
| 7 | 已过期 | 可重新上架 |
| 8 | 违规下架 | 强制下架落点；卖家可二次申请 |

### 2.5 `trade_point` 关键字段

`audit_status`：0=待审 / 1=通过 / 2=驳回；`status`：1=启用 / 0=停用；`source`：1=官方 / 2=用户提交 / 3=高德搜索落库；`safety_score` 0–100；`safe_tags` JSON 数组；`guide_text` 图文指引。

### 2.6 配置项（`application.yml`）

```yaml

    role-flag: 8
    user-ids: ${ERSHOU_ADMIN_USER_IDS:}
  review:
    realtime-enabled: true
    online-ttl: 90s

    violation-relist-enabled: true   # 源码已定义该属性，但当前没有引用点（以源码为准）
    done-keep-window: 24h
```

## 三、审核工作台（`AdminAuditController`，10 个接口）

类级路径 `/api/v1/admin`。所有方法第一行都是 `adminAuthService.requireAdminId()`（除批量商品接口在参数里取 operatorId）。

### 1. 工作台概览（待办统计）
- **方法与路径**：`GET /api/v1/admin/dashboard`
- **鉴权**：需运营权限
- **请求参数**：

| 位置 | 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| — | — | — | — | 无参数 |

- **请求体**：无
- **响应示例**：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "pendingItems": 12,
    "pendingPoints": 3,
    "onSaleItems": 128,
    "rejectedItems": 9,
    "totalItems": 320,
    "totalUsers": 540,
    "bannedUsers": 2,
    "todayOperations": 31,
    "totalOrders": 87,
    "activeOrders": 5,
    "doneOrders": 70,
    "riskOrders": 2,
    "todayOrders": 6,
    "disabledPoints": 4
  },
  "traceId": "trace-xxx"
}
```

- **业务规则 / 校验**：
  - 14 个 `count(*)`，字段含义：`pendingItems`=商品 `status=1`；`pendingPoints`=点位 `audit_status=0`；`onSaleItems`=商品 `status=2`；`rejectedItems`=商品 `status=6`；`totalItems`/`totalUsers`=全表；`bannedUsers`=用户 `status=3`；`todayOperations`=今天 00:00 起的 `sys_audit_log` 条数；`totalOrders`/`activeOrders(1,2)`/`doneOrders(3)`/`riskOrders(6,7)`/`todayOrders`；`disabledPoints`=点位 `status=0`。
  - 结果走 Redis 读缓存 `ershou:admin:dashboard`（`JsonCache.getOrLoad`），TTL `ershou.cache.dashboard-ttl`（默认 30 秒，写入时再叠加 0~10% 随机抖动防雪崩）。
  - 每次后台写操作 `AuditLogService.record` 在**事务提交后**删除该缓存；**不写审计的操作**（如 `cleanup-empty`）不会主动删缓存，最多延迟 30 秒。
  - 缓存不可用（Redis 异常 / `ershou.cache.enabled=false`）时自动降级为回源 DB，缓存不参与正确性。
- **可能错误码**：`10002`、`10003`、`90001`。

### 3. 商品审核通过
- **方法与路径**：`POST /api/v1/admin/audit/items/{id}/approve`
- **鉴权**：需运营权限
- **请求参数**：

| 位置 | 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| path | `id` | long | 是 | 商品 id |

- **请求体**：无
- **响应示例**：

```json
{"code":0,"message":"ok","traceId":"trace-xxx"}
```

- **业务规则 / 校验**：
  - 商品不存在 → `30001`。
  - 条件更新 `UPDATE item SET status=2, audit_result=1, audit_reason='人工复核通过', reject_code=NULL WHERE id=? AND status=1`；返回 0 行 → `60001`，message=`仅“审核中”的商品可以通过`（重复点通过也走这里，不是 61001）。
  - 成功后：
    - 事务提交后同步 ES 索引（`ItemIndexService.syncById`）并失效商品缓存/地图在售数（`CacheEvictor.itemChanged`）；
    - 登记进「上架审核」页：`reviewService.onItemLiveOptimistic(itemId, type)`。`type` 判定：approve 前读到的商品状态为 8，或（实际主要靠这条）`sys_audit_log` 中存在该商品 `module=item` 且 `action in (force-offline, review-item-offline)` 的任一记录 → `TYPE_VIOLATION_RELIST(4)`，否则 `TYPE_NEW(1)`（历史查询异常时按非违规处理）。要判断的是「曾经违规过」而不是「这次从哪个状态来」：`applyRelist` 和 AI 转人工都会把商品置成 1，光看前状态分不出来。
    - 落审计日志 `module=item, action=approve, target=item#{id}`，before 记录旧 `status/auditReason`，after 记录 `status=2, auditResult=1, auditReason=人工复核通过`。
- **可能错误码**：`10002`、`10003`、`30001`、`60001`、`90001`。

### 4. 商品审核驳回
- **方法与路径**：`POST /api/v1/admin/audit/items/{id}/reject`
- **鉴权**：需运营权限
- **请求参数**：

| 位置 | 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| path | `id` | long | 是 | 商品 id |

- **请求体**：模板 code 与补充说明**至少填一个**

```json
{ "reasonCode": "PROHIBITED", "reason": "疑似管制刀具" }
```

- **响应示例**：

```json
{"code":0,"message":"ok","traceId":"trace-xxx"}
```

- **业务规则 / 校验**：
  - `reasonCode` 取「驳回原因模板」的 `code`（见接口 6）；`reason` 为补充说明。二者组合规则（`AuditReasons.compose`）：
    - 模板 code 命中 + 补充说明为空（或与模板 label 完全相同）→ 理由 = 模板 label；
    - 模板命中 + 有补充说明 → `label + "：" + detail`；
    - 模板未命中（为空/未知 code）+ 补充说明非空 → 直接用补充说明；
    - 两者都为空（或 code 未知且无说明）→ `60003`。
  - 商品不存在 → `30001`。
  - 条件更新 `... SET status=6, audit_result=2, audit_reason=?, reject_code=? WHERE id=? AND status=1`；0 行 → `60001`，message=`仅“审核中”的商品可以驳回`。
  - 成功后同步索引 + 失效缓存；审计 `action=reject`，after 记录 `status=6, auditResult=2, rejectCode, auditReason`。
- **可能错误码**：`10002`、`10003`、`30001`、`60001`、`60003`、`90001`。

### 5. 商品批量通过 / 驳回
- **方法与路径**：`POST /api/v1/admin/audit/items/batch`
- **鉴权**：需运营权限
- **请求参数**：无 query/path 参数
- **请求体**：

```json
{ "ids": [101, 102, 103], "action": "approve" }
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `ids` | long[] | 是 | 至少 1 条（`@NotEmpty`，提示「请至少选择一件商品」）；服务端过滤 null 并去重 |
| `action` | string | 是 | `approve` / `reject`，服务端 `trim().toLowerCase()` |
| `reasonCode` | string | action=reject 时按规则必填一个 | 驳回模板 code |
| `reason` | string | 同上 | 补充说明 |

- **响应示例**：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "success": 2,
    "failed": 1,
    "failures": [
      { "id": 103, "reason": "状态不是“审核中”（在售）" }
    ]
  },
  "traceId": "trace-xxx"
}
```

- **业务规则 / 校验**：
  - `ids` 为空 → `10001`「请至少选择一件商品」；`action` 为空 → `10001`「请指定审核动作」。
  - `action` 不是 `approve`/`reject` → `10001`「action 只能是 approve 或 reject」。
  - `action=reject` 时**循环前**先 `compose` 驳回理由，模板与说明都为空 → `60003`（整批直接失败）。
  - 逐条独立处理，**不整批回滚**；判题顺序：
    1. 商品不存在 → failure `商品不存在`；
    2. 状态不是 1 → failure `状态不是“审核中”（<statusText>）`；
    3. 条件更新返回 0 行 → failure `已被其他运营处理`；返回 1 行 → `success++` 并同步索引/失效缓存。
  - 单条审计日志 `module=item, action=batch-approve|batch-reject, targetId=null`；before 记录 `ids`，after 记录 `success/failed/reasonCode/reason`。
  - **源码现状提醒**：批量通过**不会**调用 `ItemReviewService` 登记「上架审核」页（单条通过才会），实现时若要求一致应补上（以源码为准）。
- **可能错误码**：`10001`、`10002`、`10003`、`60003`、`90001`（逐条失败通过 `data.failures` 表达，不是顶层 code）。

  - 入队时会先刷新商品的上架快照（`last_live_title` / `last_live_desc_hash`），并推送 WS `queued`。
  - 启动任务 `ItemReviewBackfillRunner`（`@Order(100)`，`ApplicationRunner`）在应用启动时自动执行一次，`limit=500`；失败只告警、不阻塞启动。
  - 同一逻辑存在的原因是「完整性」：上线前已有商品或某次入队异常被吞，都会让「每条都被看过」的保证失效且无报错。
- **可能错误码**：`10002`、`10003`、`90001`。

## 六、上架审核（review）业务流程

> 产品口径（源码 `ItemReviewService` 类注释，2026-10-02 定）：**商品上架不拦截**，发布成功即在售、立刻可搜可买；这个页面保证「每一条上架到在售的商品都被审核员看过」。

### 6.1 队列的写入来源

| 场景 | `review_type` | 触发点 | 商品状态 |
| --- | --- | --- | --- |
| 新发布 | 1 新上架 | `ItemService.publish` 落库后若 `status=2` | 2 在售 |
| 在售期间改名/改描述 | 2 改名/改描述 | `ItemService.update` → `onContentMaybeChanged`（只认标题/描述变化，改价格/库存/图片不算） | 2 在售 |
| 已下架(5)/已过期(7) 重新上架 | 3 到期重新上架 | `ItemService.relist` | 2 在售 |
| 违规下架(8) 二次申请 | 4 违规后二次申请 | 卖家申请 → 商品置 1（审核中）；运营在审核工作台通过 → 落 2 并登记 | 2 在售 |
| 存量导入 | 5 存量导入 | 迁移脚本按「已审核」建档；启动任务/接口 25 补登按「待审」 | 2/3 |

关键实现规则：

1. **一个商品只保留一条 `item_review` 记录**（`uk_item`），重新入队时 `revision += 1`、`first_queued_at` 保留最早值、`queued_at` 刷新为当前时间；`status` 重置为 0、清空 `reviewer_id/reviewed_at/review_action/claimed_at`。
2. 入队时**先** `UPDATE item SET last_live_title=当前标题, last_live_desc_hash=MD5(描述)`——这两列代表「审核员已经看过的那一版」，下次改名对不上就能被识别。
3. 改名入队时 `title` 快照取**改之前**的 `item.last_live_title`（要能看到「从什么改成了什么」），且取快照必须发生在覆盖快照列之前。
4. **入队失败绝不影响发布**：所有入队入口 `try/catch` 吞异常并 `log.warn`，绝不把卖家看到「发布失败」。
5. 推送必须 **事务提交后**（`TxHooks.afterCommit`）：读接口走另一连接，未提交就推会推一条点进去看不到的假消息。
6. `resetOnRelistApply`：卖家二次申请上架时，把 `status=1` 的记录重置回 `0`（改完内容再申请，不能算「已审核过」）——当前 `ItemService.applyRelist` 未显式调用它（以源码为准）。

### 6.2 列表可见性（两条队列各管一段）

| 队列 | 入口 | 商品状态 | 目的 |
| --- | --- | --- | --- |
| 审核工作台 | `GET /api/v1/admin/audit/items` | 默认 1（审核中） | 决定「能不能上架」：违规二次申请、AI 转人工 |
| 上架审核页 | `GET /api/v1/admin/review/feed` | 只含 2/3 | 决定「挂着的内容要不要撤」：事后巡检 |

因此上架审核页**永不出现 `status=1`**（那是审核工作台的活）；反过来，`status=4/5/7/8` 的商品即使有审核记录也不在 `feed` 里（「已不在售的不出现在列表」）。仍留在列表里的记录 `actionable=true`，按钮永远可点。

### 6.3 处置动作与状态流转

| 动作 | 接口 | item 状态变化 | item_review 变化 | 副作用 |
| --- | --- | --- | --- | --- |
| 已审核 | `POST .../reviewed` | 不变 | `status=0→1`，`review_action=1` | 同步无、只归档；审计 `review-item-reviewed`；WS `handled` |
| 下架 | `POST .../offline` | `1/2/3/6 → 5` | 置 `status=1, review_action=2`（只按 item_id） | 清锁库/机审字段；作废进行中面交单；同步 ES + 失效缓存；审计 `review-item-offline`；WS `handled` |
| 强制下架（违规） | `POST /admin/items/{id}/offline` | `1/2/3/6 → 8` | 不写 item_review | 作废面交单；审计 `force-offline` |
| 审核通过（工作台） | `POST /admin/audit/items/{id}/approve` | `1 → 2` | 重新入队（type 1 或 4） | 同步 ES + 失效缓存；审计 `approve`；WS `queued` |
| 审核驳回（工作台） | `POST /admin/audit/items/{id}/reject` | `1 → 6` | 不写 item_review | 审计 `reject` |

状态可处置性：

- `ACTIONABLE_STATUS = {1,2,3,6}`——只有这四种状态的商品允许审核页下架（`downlist` 的 SQL 条件），对应 `VO.actionable=true`。
- 上架审核页列表本身只查 `status in (2,3)`，所以实际暴露的是「在售 / 已锁定」两类。
- 已售出(4)、已下架(5)、已过期(7)、违规下架(8)：下架接口返回 0 行 → `61001`。
- 重复处置（同一条已被别人点过）：`markReviewed` 条件更新 0 行 → `61001`；`downlist` 商品已不可下架 → `61001`。
- `61002 REVIEW_NOT_ACTIONABLE` 已定义但当前无抛出处，实现时可保留定义、不必强制抛出（以源码为准）。

### 6.4 实时推送（WebSocket）

- 地址：`ws://<host>/ws/admin/review?token=<Sa-Token>&nickname=<昵称>`（`nickname` 仅用于在线名单展示，可选）。
- 握手鉴权：query `token` 或请求头 `Authorization: Bearer ...`；无 token/无效 → 401；有效但非运营 → 403（身份没错、权限不够）。`ershou.review.realtime-enabled=false` 时该 handler **根本不注册**，前端应退回手动刷新。
- 服务端 → 客户端（JSON 文本帧）：

```json
{"type":"ready","data":{"userId":3,"instanceId":"a1b2c3d4","onlineReviewers":2}}
{"type":"queued","data":{"pending":12,"itemId":1024,"reviewTypeText":"新上架","onlineReviewers":2}}
{"type":"handled","data":{"pending":11,"itemId":88,"onlineReviewers":2}}
{"type":"violation-applied","data":{"pending":12,"itemId":77,"title":"某商品","pendingAudit":5}}
{"type":"pong","data":{"ts":1780000000000}}
{"type":"error","data":{"message":"不支持的消息类型：xxx"}}
```

  - `queued` 的实际字段是 `pending/itemId/reviewTypeText/onlineReviewers`；`AdminReviewWebSocketHandler` 类注释里写的 `item:{…ItemReviewVO…}` 与实现不一致，**以实际 `broadcastQueued` 为准**。
  - `pending` 每次现算（不是增量），避免多事件乱序让前端数字倒退。
  - `handled` 只带 `itemId`，前端按 id 把该行移出列表。
  - `violation-applied` 由卖家二次申请上架触发，携带 `pendingAudit`（审核工作台 `status=1` 条数），用于同时刷新两个队列的角标。
- 客户端 → 服务端只支持 `{"type":"ping"}`：刷新 `lastSeen` 与 Redis 在线名单，并回 `pong`。
- 在线名单：Redis Hash `ershou:admin:review:online`（field=userId、value=昵称），每次连接/心跳刷新 TTL `ershou.review.online-ttl`（默认 90s）。
- 跨实例：本机 session 直推 + Redis Pub/Sub `ershou:admin:review:channel` 广播；订阅回调按 `instanceId` 过滤回声。**广播是「频道级」的，不做 userId 过滤**——所有审核员必须看到同一条新上架。
- 兜底清理：每 60 秒摘掉 `!session.isOpen()` 的会话；源码注释约定客户端 **15 秒一次 ping**（服务端不把 `lastSeen` 超时当断开）。
- 推送失败只影响实时性，**不影响落库**（`try/catch` + `log.debug/warn`）。

### 6.5 前端必须处理的数字口径

- 顶部 `pending` 与列表 pending 条数**必须一致**（同一 SQL 口径：`status=0` 且商品在 2/3）。
- `stalePending` 用于解释「待审数自己变小」——商品被卖掉/被卖家下架，不是审核员误点。
- 处置完的条目在列表里保留 24 小时（`done-keep-window`），点了之后不会瞬间消失。

### 7.4 事务与并发要点（照抄才不会出错）

1. 所有状态流转一律用**条件更新**（`WHERE status = ...`），不要「先查后改」；返回 0 行即视为并发失败，抛对应业务码。
2. 组合顺序：`条件更新 → 审计 → 推送/缓存/索引`，其中**索引同步、缓存失效、WS 推送、删除概览缓存全部放 `TxHooks.afterCommit`**。
3. 批量处置：外层 `@Transactional`，逐条 `try/catch` 收集失败，**不因单条失败回滚整批**。
4. 下架/强制下架必须 `closeActiveOrders(itemId, "商品已被平台下架，本次约面交自动作废")`，否则已锁库的待面交单永久卡住。
5. 审计失败（`sys_audit_log` 写失败）只 `warn`，不能影响主流程。
6. 缓存失效的时机同样要在事务提交后（`AuditLogService` 与 `CacheEvictor` 的注释都强调：提前删会被并发读用旧值回填）。

### 7.5 一致性自检清单（实现后逐条验证）

- [ ] 上架审核「已审核」重复点 → `61001`；「下架」已售出/已下架商品 → `61001`。
- [ ] 审核页下架商品后：`item.status=5`、锁库字段清空、进行中面交单被作废、ES 已同步。
